# 과제 요구사항 점검 (Audit)

본 문서는 프로젝트가 과제 요구사항을 어느 정도 충족했는지 점검하고, 현재 남아 있는 한계를 함께 정리하기 위해 작성하였다.

평가 기준은 다음과 같다.

* ✅ 충족: 요구사항을 충분히 만족
* 🟡 부분 충족: 구현은 했지만 한계가 존재
* ❌ 미충족: 구현하지 못함

---

# 1. RL 문제 정의

| 항목 | 구현 내용 | 평가 |
| --- | --- | --- |
| 목표(Objective) | 비용과 콜드스타트 최소화 | ✅ |
| State | 과거 부하, 현재 인스턴스 수, 이용률, 시간 정보 | ✅ |
| Action | Warm 인스턴스 수 조정 | ✅ |
| Reward | 비용·콜드스타트·유휴 자원 패널티 | ✅ |
| Transition | Azure Functions 트레이스 재생 | ✅ |
| Episode | 1일(1440 step) | ✅ |

### 점검 결과

강화학습 문제를 State–Action–Reward–Transition 구조의 MDP로 정의하였다.

다만 실제 서버리스 환경의 모든 정보를 관측할 수 있는 것은 아니다. 특히 미래 요청 정보는 관측되지 않으며, spiky 시나리오에서는 이 부분이 성능 한계로 나타났다.

---

# 2. 실험 설계

| 항목 | 구현 내용 | 평가 |
| --- | --- | --- |
| 알고리즘 비교 | DQN, PPO | ✅ |
| Baseline 비교 | Fixed, HPA, Seasonal, Oracle | ✅ |
| 동일 평가 지표 | 모든 방법 동일 메트릭 사용 | ✅ |
| Reward 가중치 실험 | w_cold 스윕 수행 | ✅ |
| 다중 Seed 실험 | 5개 Seed 사용 | 🟡 |

### 점검 결과

알고리즘과 베이스라인을 동일한 테스트 구간에서 비교하였다.

다만 seed 수가 5개로 많지 않기 때문에 결과 분산을 충분히 측정했다고 보기에는 한계가 있다.

---

# 3. 재현성

| 항목 | 구현 내용 | 평가 |
| --- | --- | --- |
| 데이터 재생성 | data_prep.py 제공 | ✅ |
| Seed 고정 | random, numpy, torch 고정 | ✅ |
| 결정론적 평가 | 동일 test 구간 사용 | ✅ |
| 결과 저장 | metrics, model, plot 저장 | ✅ |
| 환경 독립성 | 특정 라이브러리 버전에 영향 가능 | 🟡 |

### 점검 결과

동일 환경에서는 실험 결과를 재현할 수 있다.

다만 PyTorch 버전이나 실행 환경(CPU/GPU)에 따라 세부 결과가 달라질 가능성은 남아 있다.

---

# 4. 결과 분석

| 항목 | 구현 내용 | 평가 |
| --- | --- | --- |
| 학습 곡선 시각화 | 수행 | ✅ |
| 방법별 성능 비교 | 수행 | ✅ |
| 95% 신뢰구간 | 계산 | ✅ |
| 통계적 비교 | Welch 비교 수행 | ✅ |
| 통계적 강건성 | Seed 수 제한 | 🟡 |

### 점검 결과

실험 결과를 단순 수치 비교가 아니라 그래프와 통계 지표를 이용해 분석하였다.

다만 표본 수가 적기 때문에 통계적 결론은 신중하게 해석할 필요가 있다.

---

# 5. 결과 해석

| 항목 | 구현 내용 | 평가 |
| --- | --- | --- |
| 시나리오별 분석 | steady / spiky / bursty | ✅ |
| 알고리즘 비교 | DQN vs PPO | ✅ |
| 실패 사례 분석 | PPO 붕괴, spiky 한계 분석 | ✅ |
| 일반화 수준 | 제한적 | 🟡 |

### 점검 결과

결과가 왜 나왔는지에 대한 해석을 시도했고, 특히 spiky 시나리오를 통해 상태 정보의 중요성을 확인하였다.

다만 세 개의 워크로드만 사용했기 때문에 모든 서버리스 환경에 일반화할 수 있다고 보기는 어렵다.

| 평가 항목 | 결과 | 비고 |
| --- | --- | --- |
| RL 문제 정의 | 충족 | State, Action, Reward, Transition 정의 |

### 결론

프로젝트는 과제의 핵심 요구사항을 전반적으로 충족하였다.

다만 seed 수가 적고 환경을 단순화하여 모델링했기 때문에 결과 해석에는 주의가 필요하다.
특히 PPO는 충분한 튜닝 없이 비교되었으므로, 본 결과는 "이번 설정에서 DQN이 더 안정적으로 동작했다"는 수준으로 해석하는 것이 적절하다.
